## 1. 背景与问题

### 1.1 产品定位

「文火（Wenhuo）」是一款**本地优先的桌面端长篇写作工作台**，面向长篇小说、网络连载、同人与非虚构长篇作者，以「项目 / 卷 / 章」为基本结构，把写作、存档、设定检索与成稿导出收敛在一个窗口内。

- 产品名：文火
- 英文代号：Wenhuo
- 应用 ID：`com.wenhuo.app`
- Slogan：把长篇写完
- 副标题：本地优先的长篇写作工作台

一句话定义：**让长篇作者在一个窗口里走完「写、存、查、导」四件事。**

它**不是**：通用笔记软件、在线协作工具、云文档、AI 代写工具、电子书阅读器、知识库。

### 1.2 要解决的四个真实问题

| 问题 | 具体表现 | 现有工具为何解决不好 | 文火的回答 |
| --- | --- | --- | --- |
| 写得下去 | 几十万字挤在一个文档里，输入延迟、样式错乱、目录要手维护 | Word 大文档卡顿；Typora 无项目结构；笔记软件没有卷章 | 单章独立文档 + 卷章树，只渲染当前章 |
| 丢不了稿 | 忘记保存、崩溃、误覆盖、断电；想回到昨天那版很难 | Word 自动恢复不可控；网文工具绑定云端账号 | 800ms 自动保存 + 快照 + 崩溃恢复 + 本地备份 |
| 设定找得到 | 人物、地点、组织、时间线散在多个文档；写到一半要切窗口翻"她徒弟叫什么" | 通用笔记无"设定 ↔ 章节"关联 | 设定卡 + 章节双向关联 + 与正文统一搜索 |
| 导出不折腾 | 投稿 / 成书要手动拼章节、重排目录 | 多数工具只导单文档 | 卷章结构一键合并导出 TXT / MD / EPUB |

### 1.3 差异化

1. **本地优先、无账号、无云**：数据库与稿件全部在本机，不登录、不联网也能用。
2. **中文长篇语境**：汉字计数、中文首行缩进、中文标点与排版、中文全文搜索（不依赖英文分词假设）。
3. **单章编辑**：结构上避免"一个巨型文档"，性能与心智负担都可控。
4. **自动保存 + 快照**：默认安全，不需要用户"记得存"。
5. **设定与章节关联**：人物/地点/组织/物品卡可挂到章节，可反向查询"这个角色出现在哪些章"。
6. **一键成稿导出**：卷章层级、目录、标题层级原样保留。

### 1.4 首版边界（v0.1）

- 首版聚焦「通用核心 + 小说/网文增强」，非虚构的引用、脚注、文献库放 P1。
- 项目创建时可选「网文 / 小说 / 非虚构」，仅改变默认目标、侧栏模块与导出模板，**不是三套代码**。
- 周期：4 周主线 + 1 周缓冲；先打通 Walking Skeleton 纵向链路，再横向铺功能。

### 1.5 术语约定

| 术语 | 含义 |
| --- | --- |
| 项目 | 一部作品，独立数据库记录与独立附件目录 |
| 卷 | 项目下的最大分组，可多卷，可缺省为一卷 |
| 章 | 编辑与保存的最小单位，拥有独立正文、状态、摘要 |
| 设定卡 | 人物 / 地点 / 组织 / 物品的统一称呼，含结构化字段与自由描述 |
| 快照 | 某一章在某一时刻的正文副本，分手动与自动 |
| 今日字数 | 当日净新增字数，按写作会话增量累计 |
| 连续写作天数 | 从今天（或昨天）向前连续的"有字数产出"天数 |

## 2. 目标用户

### 2.1 用户分层

| 分层 | 特征 | 主诉 | 首版优先级 |
| --- | --- | --- | --- |
| P1 网文连载作者 | 日更 4000–8000 字，单章 2000–4000 字，卷章结构，追读压力大 | 别丢稿、今天写了多少、上一章写了啥 | 最高（首要画像） |
| P1 同人作者 | 中短篇连载，设定密集，常多坑并行 | 设定管理、快速切项目 | 高 |
| P2 出版向小说作者 | 章更长，重结构、场景、人物关系与版本对比 | 大纲、版本回退、DOCX/PDF 投稿 | 中（首版保结构，版本对比放 P1） |
| P3 非虚构 / 长篇论述作者 | 章—节—小节多层目录，重引用与脚注 | 目录层级、引用脚注、DOCX 交付 | 低（首版仅保证层级与导出可用） |
| P4 隐私敏感作者 | 不信任云文档，希望稿子只在本机 | 离线、无账号、可自行备份 | 高（架构层面即满足） |

### 2.2 典型画像

**画像 A：日更网文作者（首要）**
- 每天晚上 21:00–24:00 写 2–3 章，白天用手机看数据。
- 关心：昨天写到哪、这一章多少字、今天还差多少、连续更了多少天。
- 电脑是 Windows 笔记本，装过 Word、墨者，嫌"要登录、有广告、稿子在别人服务器"。

**画像 B：出版向小说作者**
- 一年写一本，先写大纲和人物，再逐章推进，经常回头改前面的章节。
- 关心：改坏了能不能退回去、人物关系有没有前后矛盾、最后能不能交一份像样的 DOCX。

**画像 C：非虚构作者**
- 章—节结构，大量资料与引文，最后交 Word。
- 关心：层级目录、资料与正文的对应、文献不丢。

### 2.3 非目标用户

- 需要多人实时协作、评论、审批流的团队。
- 需要云端多端同步、手机续写的用户。
- 需要 AI 生成正文的用户（本产品不提供代写）。
- 只需要 Markdown 笔记、双链知识库的用户。

## 3. 核心场景

### S1 日更：从打开到存稿（最高频）

- **触发**：晚上打开电脑，继续写连载。
- **前置**：已有项目，昨天最后一章状态为"修改中"。
- **主流程**：
  1. 启动 → 项目书架，最近编辑的项目置顶，显示总字数与进度。
  2. 进入项目 → 自动定位到上次编辑的章节。
  3. 顶栏显示"今日 0 字 / 目标 4000 字"。
  4. 新建一章或续写 → 正文输入，约 800ms 停顿后自动保存，顶栏变"已保存 21:34"。
  5. 中途切到设定栏查一个配角名，再切回，光标与内容不丢。
  6. 写完把章节状态改为"完成"，右侧填一句章节摘要。
  7. 底栏显示本章字数、今日字数、是否已保存。
- **成功判据**：全程无需手动保存；任意时刻强杀进程，重启后最多丢 1 秒输入。

### S2 写崩了要回退

- **触发**：改了三章，发现越改越差，想回到两小时前。
- **主流程**：右栏「快照」→ 列表按时间倒序，含"自动 / 手动"标记与字数 → 点选预览正文 → 确认恢复。
- **规则**：恢复是**覆盖式**的，会直接替换当前正文且不自动备份；确认框明确提示「如需保留当前版本，请先给当前正文留个快照」。
- **成功判据**：3 次点击内回到目标版本；若用户先手动留档，恢复后仍可回到恢复前的版本。

### S3 写作中查设定

- **触发**：写到"他回到青云观"，忘了观主法号。
- **主流程**：左栏「人物 / 地点」或 `Ctrl+K` 全局搜索 → 输入"青云" → 结果分组为「设定」「章节」→ 点设定卡看详情，点章节跳到正文并高亮命中。
- **成功判据**：输入到跳转 ≤ 3 秒，中文 2 字关键词也能命中。

### S4 旧稿迁移

- **触发**：作者手里有一个 30 万字的 TXT / Markdown。
- **主流程**：新建项目 → 导入 → 选择"按标题拆章"规则（`第X章` / `## ` 等）→ 预览拆分结果 → 确认 → 生成卷章树。
- **成功判据**：拆分结果可预览可修正，导入后字数与原文件偏差 < 1%。

### S5 崩溃恢复

- **触发**：断电 / 强杀 / 蓝屏。
- **主流程**：重启 → 若检测到未正常关闭，弹恢复提示 → 展示"未保存草稿（时间、字数、所属章节）"→ 用户选择恢复或丢弃 → 恢复后进入对应章节。
- **成功判据**：恢复内容与崩溃前最后 1 秒内可见内容一致；丢弃也可逆（草稿进快照）。

### S6 成稿导出

- **触发**：要投稿 / 发给编辑 / 自出版。
- **主流程**：顶栏「导出」→ 向导选择格式（TXT / Markdown / EPUB）、范围（全书 / 指定卷）、是否含卷名与目录 → 选择保存路径 → 生成并提示"打开所在文件夹"。
- **成功判据**：导出文件章节顺序、标题层级、中文标点与原文一致；EPUB 能在常见阅读器中打开且目录可跳转。

## 4. 功能范围

### 4.1 优先级定义

- **P0**：首版（v0.1）必须交付，缺失即不算完成。
- **P1**：首版后第一批增强，架构需预留扩展点，但首版不实现。
- **不做**：明确排除，不进入任何版本规划（除非重新立项）。

### 4.2 项目类型模板

项目创建时选择类型，仅影响默认值与可见模块，不影响数据模型。

| 项目类型 | 默认结构 | 默认日目标 | 侧栏默认模块 | 默认导出模板 |
| --- | --- | --- | --- | --- |
| 网文 | 卷 → 章（单章 2000–4000 字） | 4000 字 | 稿件、人物、统计 | TXT（平台投稿版） |
| 小说 | 部 → 章（场景首版不实现，仅到章） | 1500 字 | 稿件、人物、地点 | EPUB / Markdown |
| 非虚构 | 章 → 节（节首版以"章内小标题"降级表达） | 1000 字 | 稿件、资料（P1） | Markdown |

> 决策：首版不做三套代码，也不做三套 schema。模板是 `ProjectTypeProfile` 配置对象。

### 4.3 P0 功能明细

#### F-01 项目书架

- **范围**：新建 / 打开 / 重命名 / 删除项目；字段含书名、作者、简介、类型、目标字数；卡片显示最近编辑时间、总字数、完成进度；最近编辑置顶；空态引导。
- **验收**：
  - 新建项目时类型、目标字数可选，创建后可直接进入工作台。
  - 删除项目需二次确认，明确提示"数据库记录与附件目录将一并删除"，并提供"先导出备份"入口。
  - 书架 100 个项目内滚动流畅，总字数由聚合查询得出而非逐章加载。

#### F-02 卷 / 章树

- **范围**：多卷多章；新建卷/章、重命名、删除、复制、拖拽排序（可跨卷）；章节状态（草稿 / 修改中 / 完成）；章节摘要；树内显示单章字数；折叠展开。
- **验收**：
  - 拖拽后刷新/重启顺序不变（持久化 `sort_order`）。
  - 删除卷需确认，卷下章节一并删除并归档到备份。
  - 复制章节生成"原标题 副本"，插入原章之后。
  - 300 章的项目树展开/滚动不掉帧（虚拟滚动）。

#### F-03 章节编辑器

- **范围**：富文本（Tiptap / ProseMirror）；标题、正文、粗体、斜体、引用、分隔线；中文首行缩进两字符、行距、版心宽度、正文字体可选；专注模式（隐左栏右栏）、打字机模式（当前行居中）；撤销/重做；章节内查找替换。
- **验收**：
  - 在 5 万字章节中输入 1000 字无明显输入延迟。
  - 中文输入法拼音组合期间不出现字符错位、重复上屏、光标跳动。
  - 专注模式下 `Esc` 退出，退出后原滚动位置保持。
  - 查找替换支持"全部替换"前给出匹配数。

#### F-04 自动保存与恢复

- **范围**：停止输入约 800ms 自动保存；切章、窗口失焦、关闭前强制 flush；崩溃后恢复未保存草稿；写入采用 SQLite 事务 + WAL；写入失败保留旧版本并提示。
- **验收**：
  - 任意时刻强杀进程后重启，恢复内容与崩溃前最后可见内容差异 ≤ 1 个输入停顿（约 1 秒）。
  - 保存状态在顶栏可见：`保存中… / 已保存 HH:mm / 保存失败（重试）`。
  - 保存失败不静默：连续 3 次失败后弹提示，并把内存草稿落盘到恢复日志。

#### F-05 快照

- **范围**：手动命名快照；自动快照（每 10 分钟或累计 2000 字，先到先触发）；快照列表、正文预览、恢复；同内容 hash 去重；自动快照保留策略。
- **验收**：
  - 手动快照可填备注，永不自动清理。
  - 内容未变化的自动快照不重复落库。
  - 恢复直接覆盖当前正文，不自动生成"恢复前"快照；确认框必须提示风险与手动留档入口。
  - 旧版本遗留的「恢复前」记录可一键清理，且不影响其它快照。
  - 单章 200 次自动快照后数据库增长可控（去重 + 保留上限生效）。

#### F-06 字数与目标

- **范围**：当前章 / 当前卷 / 全书字数；今日字数；每日目标与完成度；连续写作天数；章节字数在树与底栏展示。
- **计数规则**（全局唯一实现）：
  - 汉字（CJK 统一表意文字及扩展 A、兼容区）：每字计 1。
  - 连续拉丁字母 / 数字串：按空白与标点切分，每段计 1 词。
  - 标点、空白、换行、Emoji、控制字符：不计。
  - 全书字数 = 各章 `word_count` 之和（不做全文重算）。
  - 今日字数 = 当日各写作会话净增量之和；删除/撤销产生的负增量计负，展示时下限为 0。
- **验收**：
  - 含中英混排、全角标点、Emoji 的样本，计数结果与手工核对一致。
  - 今日字数在跨零点后自动归零（按本地时区日期切分）。

#### F-07 全文搜索

- **范围**：搜索章节标题、正文、设定卡名称与描述；结果分组、命中上下文（前后约 40 字）高亮、点击跳转并定位；搜索延迟 200ms 防抖；最小 1 字符。
- **验收**：
  - 中文 1–2 字查询（如"青云""剑"）有结果，不因分词失效。
  - 50 万字项目内搜索响应 < 300ms（P95）。
  - 结果点击后打开对应章节并选中命中文本。

#### F-08 设定库

- **范围**：人物卡（姓名、别名、身份、外貌、性格、目标、关系）、地点卡、组织卡、物品卡；自由描述 + 结构化字段；与章节多对多关联；设定内搜索与"反向引用"（该设定出现在哪些章）。
- **验收**：
  - 新建设定卡后可立即在右栏关联到当前章节。
  - 反向引用列表可点击跳转。
  - 删除设定卡时提示关联章节数，删除后关联自动清理。

#### F-09 导入导出

- **范围**：
  - 导入：TXT / Markdown，按规则自动拆章（标题正则、`##`、空行分章可选），导入前预览。
  - 导出：TXT / Markdown / EPUB；合并卷章、生成目录、保留标题层级；范围可选全书或指定卷。
- **验收**：
  - 导入 30 万字 TXT 在 5 秒内完成预览，拆分结果可在预览中合并/拆分/改名。
  - TXT 导出含卷名与章序，行距与空行规则可配置（默认：章间空一行）。
  - Markdown 导出为 `# 卷` / `## 章`，正文段落不丢失。
  - EPUB 通过 epubcheck 基础校验，`nav.xhtml` 目录可跳转，`dc:language` 为 `zh-CN`。

#### F-10 备份

- **范围**：手动导出 zip 备份（数据库 + 附件 + manifest）；自动备份到项目目录（每日首次编辑后，保留最近 N 份）；从备份恢复（整体替换前先备份当前状态）。
- **验收**：
  - 备份包可在另一台机器解压恢复，恢复后卷章、字数、快照、设定均完整。
  - 自动备份失败仅告警不阻塞写作。

### 4.4 P1 功能（首版不实现，架构预留）

1. 大纲看板（卡片式拖动编排，与章节双向同步）。
2. 时间线视图（事件 ↔ 章节）。
3. DOCX / PDF 导出。
4. 快照差异对比（diff 视图）。
5. 章节标签 / 伏笔 / 线索追踪。
6. 写作热力图（按日字数日历）。
7. 敏感词 / 错别字检查。
8. 多项目统计与年度报告。
9. 投稿模板（不同平台格式）。
10. 自定义快捷键与命令面板增强。
11. 非虚构增强：引用、脚注、文献库、表格。
12. 场景卡（小说类型：部 → 章 → 场景）。

### 4.5 明确不做

- 云同步、账号体系、在线书城、平台发布对接。
- 协同编辑、评论、批注流转。
- AI 代写 / AI 续写 / AI 改写。
- 通用知识库、双向链接、插件市场。
- 移动端 App、Web 版。
- 富媒体（图片插入正文、音频、视频）——首版仅保留附件目录与头像字段。

### 4.6 页面与信息架构

三栏工作台：

### 4.7 全局业务规则

- **保存**：草稿态在内存，落到 `chapters` 视为一次提交；保存以事务写入正文、`plain_text`、`word_count`、`updated_at`，并同步搜索索引与写作会话增量。
- **章节状态**：`draft` 草稿 / `revising` 修改中 / `done` 完成，仅影响展示与筛选，不锁定编辑。
- **排序**：卷与章均用稀疏 `sort_order`，拖拽只改被移动项与被跨越项，避免全表重排。
- **时间**：所有时间戳存 UTC 毫秒整数；"今日"按本地时区日期计算，`date_key` 形如 `2026-10-22`。
- **删除**：删除项目/卷/章前必须二次确认；删除前自动生成一份备份。
- **失败处理**：所有主进程能力统一返回 `Result<T>`（`{ ok: true, data } | { ok: false, error }`），渲染层不抛裸异常、不吞错。

## 6. 约束与假设

- 【假设】技术栈固定为 Electron + React 19 + TypeScript + SQLite（better-sqlite3）+ Tiptap；不引入服务端、账号体系与任何强依赖网络的运行时能力，首版全部功能离线可用。
- 【假设】数据层为 SQLite + WAL，所有数据库访问只在主进程，渲染进程只经 `Result<T>` 包装的 IPC 访问数据；渲染层组件不直接调用 `window.api`。
- 【假设】正文以 ProseMirror JSON 存储、纯文本冗余存储（`plain_text`），字数由纯函数从纯文本计算，不由编辑器插件实时累加。
- 【假设】单项目规模上限为 200 万字 / 1000 章，单章不超过 2 万字；同时只打开一个项目窗口。
- 【假设】设定卡每项目不超过 2000 张，快照库单项目不超过 2GB。
- 【假设】首版只交付 Windows 10/11 x64 安装包；代码避免平台特有路径拼接，但不对 macOS 做打包与签名验证。
- 【假设】开发资源为 1 人全职，周期 5 周（4 周功能 + 1 周缓冲），无专职设计与测试人力。
- 【假设】项目数据默认存放于 `%APPDATA%\wenhuo`，允许在设置中修改项目根目录；应用不主动上传任何内容。
- 【假设】网络能力（若未来引入 AI 或平台投稿）一律后置，首版构建产物不包含任何外部 API 依赖。
- 【推断】better-sqlite3 为同步 API，在主进程按请求串行执行即可满足单用户场景；预计不会成为瓶颈，因为单次保存只写一行且 WAL 下写入在毫秒级。
- 【推断】Electron 43 的原生模块 ABI 与打包工具链可能存在版本错配，因此 W1 必须产出可安装包验证，不能把该风险留到 W4。
- 【推断】Tiptap 在单章 5 万字内可保持流畅；若超出，需要在 W4 引入按段落懒加载或只读分块渲染作为兜底。
- 【推断】FTS5 的 trigram 分词对 3 字以上中文查询性能与召回均可接受；1–2 字查询走 LIKE 兜底，代价是慢一些但结果正确。
- 【推断】快照若每次存全文，50 万字项目在 2000 次快照后会显著膨胀，因此 hash 去重、限频与保留上限是必需项而非优化项。
- 【推断】用户对"无云同步"的接受度取决于备份能力，故 F-10 虽在 W3，但备份入口需在 W1 的界面骨架中预留位置。
- 【推断】中文输入法组合期间若触发保存与重渲染，会导致候选词错位与重复上屏，因此组合事件门控是 P0 硬性要求。
- 【推断】导出格式若无结构级测试，会出现"能导出但目录乱"的问题，因此导出必须做快照式断言（golden file）。
- 【推断】范围膨胀是 4 周计划的最大风险，因此 P0 清单冻结，P1 一律只进 backlog，W4 不得开工新功能。
- 【推断】验收 E2E 目标 ≥ 6 条，当前 10 条：新建项目→建卷章→中文输入→自动保存→重启恢复；写 3 章→搜索中文关键词→跳转；手动快照→修改→恢复→内容回到旧版；导入 TXT→拆章预览→导出 EPUB；删除项目→记录与附件清理；强杀进程→重启→恢复提示→内容正确；另有查找替换、完成章锁定、设置页 3 条。
