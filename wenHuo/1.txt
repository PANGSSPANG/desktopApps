长篇写作工作室 · 产品讨论总结
================================

一、项目选择
------------
方向：桌面端应用（非全栈）。
产品：长篇写作工作室，暂定名「文火」。

定位：
  本地优先、面向长篇小说 / 网文 / 长文作者的章节化写作工作台。
  解决“写得下去、丢不了稿、设定找得到、导出不折腾”。

不是通用笔记软件，也不是在线协作工具。

核心价值：
  1. 单章编辑，避免几十万字一个大文档卡顿。
  2. 自动保存 + 快照 + 恢复，防丢稿。
  3. 卷 / 章结构 + 字数目标 + 写作统计，符合长篇写作节奏。
  4. 人物、地点、时间线与章节关联。
  5. 全文搜索 + 一键导出。

明确不做：
  云同步、账号、在线书城、AI 代写、协同编辑、通用知识库、移动端。


二、为什么比电子阅读器复杂
--------------------------
电子阅读器：书 / 进度 / 设置，阅读、翻页、目录、导入、续读。

长篇写作工作室：
  项目 / 卷 / 章 / 人物 / 地点 / 时间线 / 快照 / 统计 / 标签
  富文本编辑、自动保存、版本恢复、拖拽目录
  防丢稿、备份、崩溃恢复
  全书搜索 + 设定搜索
  TXT / Markdown / EPUB / DOCX / PDF 导出
  每日字数、目标、连续写作、章节字数

复杂度来自四条真实链路：
  编辑器 + 版本快照 + 关系数据 + 导出。


三、目标用户与痛点
------------------
用户：
  - 网文作者、同人作者
  - 长篇小说作者
  - 非虚构 / 长篇论述作者
  - 不信任云文档、希望稿子完全在本地的作者

痛点：
  - Word 写几十万字后卡顿、样式乱、版本混乱
  - 设定、人物、大纲散落在多个文档
  - 忘记保存、崩溃丢稿
  - 回退到昨天版本很麻烦
  - 导出投稿格式要手动拼章节
  - 通用笔记软件没有卷/章/字数目标/写作统计


四、网文、小说、非虚构的区别
----------------------------
建议：一个产品 + 项目类型模板，不做三套代码。

网文连载：
  卷 → 章，单章 2000–4000 字，日更 4000–8000 字。
  重点：自动保存、日更字数、连续天数、章节状态、人物连续性。
  导出：TXT / 平台投稿格式。

出版小说 / 一般小说：
  部 → 章 → 场景，章节更长。
  重点：大纲、场景卡、人物关系、时间线、版本对比。
  导出：DOCX / PDF / EPUB。

非虚构 / 长篇论述：
  章 → 节 → 小节，重目录层级。
  重点：资料笔记、引用、脚注、表格、文献管理。
  导出：DOCX / PDF，保留引用与脚注。

共性：
  项目、卷章树、富文本编辑、自动保存、快照、全文搜索、字数统计、导出。

首版建议：
  先做“通用核心 + 小说/网文增强”。
  非虚构的引用、脚注、文献库放 P1。
  项目创建时可选“网文 / 小说 / 非虚构”，只改变默认目标、侧栏模块和导出模板。


五、竞品与差异化
----------------
  Scrivener：长篇结构成熟，但贵、英文语境重、UI 老。
  Word：普及，但大文档卡、版本管理弱、设定管理弱。
  Obsidian：本地、Markdown、插件强，但通用笔记，不是写作工作流。
  墨者 / 橙瓜：中文网文场景强，但账号/云/广告/平台绑定。
  Typora：Markdown 舒服，但没有项目管理、版本、设定、统计。
  Ulysses：体验好，但订阅制、苹果生态。

差异化：
  本地优先、无账号、无云；中文长篇语境；单章编辑；自动保存 + 快照；
  设定与章节关联；一键导出。


六、功能范围
------------
P0 首版：

  1. 项目书架：新建/打开/删除；书名、作者、简介、类型、目标字数；
     最近编辑时间、总字数、进度。
  2. 卷 / 章树：多卷多章；拖拽排序、重命名、删除、复制；
     状态：草稿 / 修改中 / 完成；章节摘要。
  3. 章节编辑器：富文本（Tiptap / ProseMirror）；标题、正文、粗体/斜体、
     引用、分隔线；中文首行缩进、行距、版心宽度、字体；
     专注模式 / 打字机模式；撤销/重做、查找替换。
  4. 自动保存与恢复：输入停止约 800ms 自动保存；切章、失焦、关闭前强制保存；
     崩溃后恢复；本地 .bak 与 SQLite WAL。
  5. 快照：手动命名快照；自动快照（每 10 分钟或每 2000 字）；列表、预览、恢复；
     差异对比可放 P1。
  6. 字数与目标：当前章/卷/全书字数；今日字数、连续写作天数；每日目标；
     中文按汉字计数，英文按单词计数。
  7. 全文搜索：章节标题、正文、人物、地点、大纲；命中上下文、跳转；
     中文使用 SQLite FTS5 trigram 或应用层分词。
  8. 设定库：人物卡（姓名、别名、外貌、性格、目标、关系）、地点卡、组织卡、
     物品卡；章节关联；搜索与反向引用。
  9. 导入导出：导入 TXT / Markdown 自动拆章；导出 TXT / Markdown / EPUB；
     合并卷章、生成目录、保留标题层级。
  10. 备份：手动 zip；自动备份到项目目录；恢复。

P1：
  大纲看板、时间线、DOCX/PDF 导出、快照 diff、章节标签/伏笔/线索、
  写作热力图、敏感词/错别字检查、多项目统计、投稿模板、自定义快捷键。


七、界面
--------
三栏工作台：

  顶栏：项目名 / 保存状态 / 今日字数 / 导出 / 设置
  左栏：稿件（卷/章）、大纲、人物、地点、时间线、统计
  中央：卷/章标题 + 正文编辑区
  右栏：章节信息 / 状态 / 摘要 / 关联人物 / 快照 / 字数
  底栏：本章字数 · 今日目标 · 已保存

关键页面：
  项目书架、项目工作台、专注模式、大纲看板、人物/地点详情、
  时间线、写作统计、快照历史、导出向导。

视觉：
  暖色纸张、衬线正文、低干扰工具栏，有“写作桌”的感觉。


八、数据模型
------------
SQLite（better-sqlite3）+ WAL；章节正文存 TEXT，图片/附件存项目目录。

  projects：id, title, author, genre, synopsis, target_words,
            created_at, updated_at, settings_json
  volumes：id, project_id, title, sort_order
  chapters：id, volume_id, title, content_json, plain_text, word_count,
            status, synopsis, sort_order, created_at, updated_at
  characters：id, project_id, name, alias, role, profile_json, avatar_path
  locations：id, project_id, name, kind, profile_json
  chapter_links：id, chapter_id, entity_type, entity_id
  timeline_events：id, project_id, title, event_time, description, chapter_id
  snapshots：id, chapter_id, kind, content_json, plain_text,
             content_hash, note, created_at
  writing_sessions：id, project_id, started_at, ended_at, words_written
  settings：key, value

搜索：FTS5 + trigram；1–2 字查询回退 LIKE 或应用层扫描。
字数：汉字按字符，英文按单词，标点不计；保存后写 word_count；
      今日字数用 session 增量，避免全量扫描。


九、技术架构
------------
  Electron 43.3.0
  React 19 + TypeScript + Tailwind + Zustand
  Tiptap / ProseMirror
  better-sqlite3 + WAL + migration
  Vitest + Playwright CDP

主进程：
  SQLite / migrations / WAL、project、chapter、search、snapshot、export、backup、
  IPC Result 包装。

渲染层：
  三栏工作台、编辑器、大纲、统计、导出向导；组件不直接调 window.api。

导出：
  TXT / Markdown 字符串拼接；
  EPUB 用 fflate 生成 zip + nav + 章节 XHTML；
  DOCX 用 docx 纯 JS 库；
  PDF 用隐藏 BrowserWindow 渲染 HTML + printToPDF。

安全：
  contextIsolation、sandbox、nodeIntegration:false；
  数据库只走主进程；导出走受控 IPC。


十、关键技术难点
----------------
  1. 中文输入法与自动保存：组合输入期间不要触发保存/重渲染；
     监听 compositionstart/end，组合结束后再保存。
  2. 中文全文搜索：FTS5 默认分词不友好；用 trigram 或二元组；1–2 字查询兜底。
  3. 快照体积：内容 hash 去重；自动快照限频；手动快照命名保留。
  4. 大项目性能：只渲染当前章；章节树虚拟滚动；搜索分页；统计聚合查询。
  5. 导出保真：卷章层级、标题、分页、目录、中文标点、段落缩进。
  6. 数据安全：SQLite WAL + 事务 + 自动备份；写入失败保留旧版本；
     崩溃恢复最近 N 分钟草稿。
  7. 原生模块打包：better-sqlite3 需与 Electron ABI 匹配；第一周就验证安装包。


十一、测试策略
--------------
单元测试：
  中文字数 / 英文单词、章节树排序、数据库迁移、快照去重、FTS 中文搜索、
  导出 HTML/EPUB 结构、备份文件生成。

E2E：
  新建项目 → 卷/章 → 中文输入 → 自动保存 → 重启恢复；
  写 3 章 → 搜索 → 跳转；
  快照 → 修改 → 恢复；
  导入 TXT → 拆章 → 导出 EPUB；
  删除项目 → 清理；
  强杀进程 → 重启恢复。

性能验收：
  50 万字项目切章 < 200ms；搜索 < 300ms；启动到书架 < 1.5s；
  自动保存不打断输入。


十二、时间预算与区别
--------------------
2 周：
  可运行骨架：项目、卷章树、编辑器、保存、重启恢复、TXT 导出。
  只能算课程 MVP；人物、搜索、快照、打包不稳。

4 周：
  完整 P0：编辑器、自动保存、快照、章节树、字数目标、全文搜索、
  人物/地点、TXT/MD/EPUB、基础测试、安装包。
  需克制范围；DOCX/PDF、时间线、大纲看板可能来不及。

8 周：
  P0 + P1：大纲看板、时间线、DOCX/PDF、快照 diff、统计热力图、
  完整 E2E、性能优化、发布级打磨。
  时间充裕但容易功能膨胀。

推荐：4 周主线 + 1 周缓冲。
  第 1 周：壳、SQLite、项目/卷章、编辑器
  第 2 周：自动保存、快照、字数、搜索
  第 3 周：人物/地点、导入导出、备份
  第 4 周：测试、性能、安装包、演示数据
  第 5 周：只修 bug 和打磨，不加功能

只有 2 周：砍掉人物/地点/时间线，把“写、存、搜、导出”做扎实。
有 8 周：再加 DOCX/PDF 和大纲看板。


十三、先框架再功能
------------------
原则：不要先画一堆空页面；先打通一条最小但真实的纵向链路。

Phase 0：Walking Skeleton（3–5 天）
  建项目 → 建卷章 → 写字 → 保存 → 重启恢复 → 导出 TXT。
  包含：Electron 壳、路由、主题；SQLite schema v1、迁移；IPC Result；
  项目列表/新建；卷章树；Tiptap；自动保存 + 重启恢复；TXT 导出。

Phase 1：写作核心
  自动保存防抖、切章保存、关闭前 flush、崩溃恢复、字数统计、今日目标、
  章节状态/摘要、手动快照+恢复、专注模式。

Phase 2：检索与设定
  全文搜索（章节+人物+地点）、人物卡、地点卡、章节关联、基础统计、大纲列表。

Phase 3：导入导出与备份
  TXT/Markdown 导入拆章、EPUB 导出、DOCX/PDF 导出、项目备份/恢复、
  导出模板（网文平台/一般稿件）。

Phase 4：打磨
  大纲看板、时间线、快照 diff、写作热力图、快捷键、命令面板、打包、E2E、性能。


十四、框架扩展点
----------------
  1. ProjectTypeProfile：网文 / 小说 / 非虚构，控制默认目标、侧栏模块、导出模板。
  2. Exporter 接口：txt / markdown / epub / docx / pdf 各自实现；首版只接 TXT。
  3. 数据库迁移：schema v1 开始，后续人物/时间线/引用都走 migration。
  4. Feature 目录：features/editor、manuscript、world、search、export；
     未完成模块用 feature flag 隐藏。
  5. 测试骨架第一天开始：字数、排序、迁移、快照；
     一条 E2E：新建 → 写 → 保存 → 重启 → 内容还在。


十五、容易踩的坑
----------------
  - 先做一堆空 UI，最后发现数据模型不对。
  - 自动保存打断中文输入法。
  - 中文全文搜索 FTS5 默认分词不行。
  - SQLite 原生模块打包问题留到最后。
  - 快照存全文导致数据库膨胀。
  - 导出格式不对，没有结构测试。
  - 功能范围膨胀，4 周做不完。


十六、产品命名建议
------------------
首选：

  中文名：文火
  英文代号：Wenhuo
  应用 ID：com.wenhuo.app
  Slogan：把长篇写完
  副标题：本地优先的长篇写作工作台

为什么是“文火”：
  - 取自“文火慢炖”，对应长篇写作需要持续、稳定、不急躁。
  - 两个字，好读、好记、好输入。
  - 有温度，和纸张、墨色、长时间写作的视觉气质很搭。
  - 不局限题材：网文、小说、非虚构都能用。
  - 可延展品牌语言：慢慢写，写很长。

备选：

  章回：适合网文/小说；直接对应章节体长篇；可能偏传统，非虚构代入感弱。
  慢墨：适合文学/长文；慢下来写字，气质安静；可能不符合日更效率诉求。
  墨匣：适合工具型写作台；作家的墨与工具箱；长篇属性不够直接。
  长卷：适合通用长篇；长卷展开，结构感强；比较常见，重名概率高。
  字舟：适合文艺向；文字如舟，载着长篇走远；偏抽象，需要副标题解释。

命名原则：
  - 2 个字优先，好读、好打、好记。
  - 不用生僻字，不要中英混排。
  - 不要直接带“写作 / 笔记 / AI”，否则像功能描述，难注册。
  - 与“长篇、章节、纸张、墨、时间”有语义关联。
  - 查商标、域名、GitHub/npm 包名、应用商店重名。
  - 避免与“墨者、橙瓜、灯果、壹写作”等混淆。

最终建议：
  产品名：文火
  英文代号：Wenhuo
  Slogan：把长篇写完
  副标题：本地优先的长篇写作工作台

如果明确做网文/小说，第二选择“章回”；
如果更文学、更安静，第二选择“慢墨”。


十七、结论与待确认
------------------
结论：
  长篇写作工作室是合适的复杂桌面项目。
  比阅读器多出编辑器、版本、关系数据、统计、导出五类真实复杂度。

当前推荐：
  暂定名“文火”；
  首版聚焦“小说/网文 + 通用核心”；
  非虚构引用/脚注放 P1；
  4 周主线 + 1 周缓冲；
  先做 Walking Skeleton，再逐步加功能。

待确认：
  1. 主要写网文、小说还是非虚构？是否都有？
  2. 实际开发时间：2 周、4 周还是 8 周？
  3. 首版是否必须 DOCX/PDF，还是 TXT/Markdown/EPUB 就够？
  4. 是否接受 better-sqlite3 原生模块？
  5. 是否只做 Windows，还是同时考虑 macOS？

下一步：
  输出 PRD、数据库 schema、页面清单、4 周迭代计划，
  从 Phase 0 的 Walking Skeleton 开始实现。
